# PaperPro 匹配度评分方法与有效性边界（2026-10-19）

**版本**：候选人端规则版本 candidate-rubric-0.3.0

**规则事实源**：app/diagnosis/rules.json

**计算源码**：app/diagnosis/scoring.py + engine.py

**专家标注/可复现评估**：app/diagnosis/calibration.py
**状态**：工程内部验证通过；**未经真实招聘样本与真实岗位结果校准，不代表经过效度认证的 HR 打分标准**。

## 1. 为什么不能直接凑百分比

经济学的多准则决策分析（MCDA）将不同属性的价值函数归一化后加权，但权重不仅取决于主观“重要”，还与该属性的可能改变量有关。真正的权重应通过具备招聘岗位知识的专家进行范围敏感的 Swing Weighting 或 AHP 成对比较，并经过一致性检验。直接让大模型随意生成分数，无法保证可复现性或数字意义。

心理测量/人员选拔强调区分三件事：
1. **内容相关性**（Content validity）：有没有覆盖岗位实际任务与任职条件？
2. **信度与结构合理性**（Reliability / Construct validity）：同样资料多次计算是否稳定？不相关身份信息、无关技能和否定句会不会污染结果？是否能区分不同证据强度？
3. **准则相关效度**（Criterion validity）：实际是否能预测独立 HR 判断、面试筛选或工作表现？这必须通过真实、分层、独立标注与留出集测量，**不能**用我们自己构造的数据证明。

## 2. 当前可解释计分公式

设目标岗位为 J，七个因素为 i：

    S(J,R) = round[100 × Σ(w_i(J) × m_i(J,R)) / Σ(岗位适用项的 w_i(J))]

- w_i 在单一岗位族群内之和为 1（没有明示的要求不自动算作候选人的缺陷）。
- m_i ∈ [0,1]：证据强度，完全由归一化后的字段和原文位置计算。
- 单纯在技能列表**声明**技能的强度小于有具体项目/工作应用文字证据；重复词汇不重复加分；否定句不算“掌握”。
- **相关工作月数**必须满足起止年月可计算且该段职位/工作职责有目标岗位职能文字证据；不相关经历不累计为相关年限。多段经历重叠按自然月集合**只计一次**；缺失或不可信任期不猜测。工作月数阈值如果来自岗位族群默认配置，必须标明非企业官方 JD。
- **岗位族群路由**优先匹配专业领域关键词；数据/算法/设计等不因通用“工程师”后缀被误分到软件岗位。优先级与关键词同存规则表。
- **否定与来源边界**：明确否定的技能、学历或职责不能成为正向证据；学历只看教育背景，行业/管理证据只看工作或项目，不用“希望进入某行业”代替从业证据。
- 原始证据、可见位置、得分系数、基本权重、实际生效权重、岗位规则版本全部随报告输出。
- 目标公司有值而目标职位和 JD 均不充分时，结果明确标注“资料证据指数（未提供岗位，不能用于岗位分层）”，绝不当成该公司的录取概率或 HR 官方分。

分级为高 ≥78、中 52–77、低 <52；**阈值是初始启发式，并非统计校准后的雇主选拔切点**。分级只取决于上面的匹配分，其他四维是解释性诊断，不偷偷改写总体分数。

## 3. 角色初版权重（尚待岗位专家给出 Swing 判断）

| 指标 | 后端/软件 | 数据/算法 | 产品 | 设计 |
|---|---:|---:|---:|---:|
| 技能 | 32% | 34% | 19% | 30% |
| 岗位职能 | 19% | 18% | 26% | 21% |
| 工作年限 | 15% | 13% | 17% | 12% |
| 项目成果 | 16% | 17% | 15% | 22% |
| 学历 | 6% | 8% | 5% | 5% |
| 行业 | 6% | 6% | 10% | 5% |
| 管理范围 | 6% | 4% | 8% | 5% |

默认岗位族群提供代理阈值；真实 JD 明确写出的要求优先。学历、管理或行业若未作为要求提出，不做额外假设或硬性扣分。不能推断政治、性别、年龄、残障或个人品行。

**限制**：这些指标可能相关，如同一段项目描述可能同时支撑技能、职能和项目；加法模型要求的偏好独立性尚未通过业务验证。因此不应把分数解释成经过统计校准的客观胜任力指标。

## 4. 已运行的内部实验（合成，不是招聘准确率）

执行：

    uv run --python 3.12 python -m pytest tests/test_scoring.py tests/test_calibration.py -q
    uv run --python 3.12 python -c "from app.diagnosis.calibration import synthetic_benchmark,perturbation_benchmark; print(synthetic_benchmark()); print(perturbation_benchmark(trials=50,seed=17))"

2026-10-19 实测：
- 4 个岗位族群 × 6 个层级 × 2 个表达变体 = **48 个情景**。
- **240 组可排序对照**，**0 次逆序、8 次同分**，严格区分率 **96.67%**，合成非逆序率 100%。
- 匹配分在场景中跨度 **90 分**。
- 50 轮 × 48 个情景 = **2400 次重评分**；对每个族群的七维权重独立做 ±20% 扰动、再归一化。
- 扰动下累计 **12000 组跨层比较，0 次逆序**；等级变化率 **1.42%**。
- 对同一简历与目标，反复运行完全确定（同日同规则版本）；不相关身份字段不改变岗位分数。
- 补充反事实：财务/设计/土木年限不自动变成后端相关年限；“2026年社会招聘”不解析成 26 年资历要求；重叠任期只计一次；岗位族群不会由泛用职位后缀误路由；否定学历、职业愿望、无关项目和“Python：不会”不加分；同级职务不自动视为晋升；新目标或新粘贴内容不会接受旧异步结果。
- AI 解释权限改为规则表中的 `narrative_codes` 与可核对的 `evidence_paths` 选择协议，服务端构建最终显示文字；即使模型返回“二〇二〇年晋升总监”等非数字化编造，也会拒绝而保留确定性报告。
- TXT/PDF 选择性导出与五维报告通过真实 Chrome E2E 另行检查。

这批情景故意分层，因此 96.67% 只表示我们构建的规则对**自身预设的层级有区分度**。它**不是** 96.67% 的 HR 一致率，更不是录用/淘汰判断的准确率，不能对外宣传为准确率。

### 第二阶段：独立反事实压力测试（规则 0.3.0）

**入口：** 项目根目录运行

    uv run --python 3.12 python -m scripts.stress_test_scoring
    uv run --python 3.12 python -m pytest tests/test_counterfactual_bench.py -q

**测试方法**：先于评分结果制定七类期望关系（技能增加应严格增分；否定技能、无关长期经历、改名与兴趣、复制相同项目证据、复制同一任职区间不得加分；可定位的应用证据应强于技能列表自述）。这套期望与岗位打分权重独立，不使用评分器生成的伪 HR 标签，也不训练权重。

设计由四种岗位族群 × 七类干预 × 20 组变化构成，每个种子 560 对。JD 的职位表述、技能排列与相关年限变化，20 组并非简单重复个人姓名。使用三个预先固定种子 1021、2026、99，共 1,680 组预注册对照（3,360 次评分），四岗位、70 种不同 JD 措辞（单个种子）。均通过预设的相等或单调性测试。**并不表示 1,680 份独立真实简历或 100% 招聘准确率。**

**先前实际抓到并修复的失败：**
- 一条项目描述原样复制三次可以凭数量增加总分 9–12 分。现对正向原文证据按规范化内容去重，不重复加权。
- 两段完全相同日期、相同职务与成果的任职记录会重复抬高项目分；现同一事实只作为一份独立证据，任职月数仍按自然月集合去重。
- JD 明确要求 Git，但全局技能词表未收录，使补充 Git 后技能分未提高；现已补齐词表，并验证各岗位默认技能必须属于词表。

**适用范围**：证明实现对特定能力证据、无关背景和重复内容的可解释性与反事实约束；不证明与真实 HR 评价、真实录用及工作绩效的统计一致性。真正检验后者依然需要独立专家/招聘数据。

## 5. 下一步如何获取真实数据并校准

**先锁定目标测量对象**：是“与专家独立匹配度评估的一致性”，还是“对真实筛选结果的预测”——两者不同。建议先做前者，后者只在取得合规的、带真实结果的数据之后做。

采用经过适当授权和匿名化的最少 **20 份多岗位简历 + 对应原始 JD**（这是 R7-1 的最低产品验收数量，不足以保证统计稳定性；真正校准需要更多独立样本）。

每组保留：
- 不含姓名、性别、年龄等非岗位信息的结构化简历与原件质量等级；
- 岗位名称和真实 JD；
- 至少 2 名**独立、盲法** HR/领域专家给出的 0–100 专家评分或逐能力项判断，记录专家间分歧；
- 预先固定 train/test 拆分；同一简历/岗位的去重指纹忽略姓名、邮箱、电话、地点与原始上传标识，重复样本（同组或跨训练/保留组）均被拒绝。近似文本重复仍需人工分组审核；
- PDF/DOCX/拍照 OCR 各自的字段准确率和遗漏率；岗位家族分层的 MAE、Spearman、成对顺序一致性、阈值误差；
- 数据获得合法来源与处理许可，禁止在公开仓库上传任何可识别个人资料。

### 在本机验证真实 HR 标注

将经授权并匿名化的 HR 标注 JSON 保存在 evaluation_private/hr_labels.json（本目录已被 Git 忽略）。顶层是 cases 数组；至少 20 例，训练与保留测试组至少各 5 例。每条记录包含：

    {
      "case_id": "anonymized-001",
      "split": "train",
      "resume": {"name": "", "title": "后端开发工程师", "skills": ["Python", "SQL"]},
      "target": {"role": "后端开发工程师", "job_description": "实际授权的目标岗位 JD"},
      "reviewer_scores": [72, 78]
    }

以上只是单条字段格式示例，不是完整数据集，也不能拿示例打分充当 HR 独立标注。case_id 不得包含姓名、电话或其他身份标识；两项 reviewer_scores 必须由不同专家独立给出，训练/保留切分必须在评分前固定。

根目录运行（完全离线、无模型调用、不修改规则表、不输出逐份私人简历）：

    uv run --python 3.12 python -m scripts.evaluate_hr_dataset --input evaluation_private/hr_labels.json

只输出训练和留出集的聚合 MAE、Spearman、成对排序一致性及专家评分差异。这个结果只能衡量相对于专家评价的一致性，不能证明真实录用概率或工作绩效预测效度。

代码已提供：
- evaluate_human_labels：要求两位独立标注员、检查样本分组、保留集差异、计算专家一致性指标；
- propose_weights：只对训练集提出新权重，在**保留集**比较误差，不能自动改写规则；
- ahp_weight_proposal：成对比较和 CR≤0.1 一致性门槛；
- swing_weight_proposal：重要性 × 可变范围，输出待专家审批权重；
- perturbation_benchmark：版本化、多场景随机扰动的敏感性测试。

**变更门槛**：只有独立留出集的证据强于当前版本，且岗位负责人审核通过，才修改 rules.json 的权重/等级阈值。即使专家评分一致，也不能直接宣称预测真实招聘结果。校准须监测小样本偏差、岗位差异、词汇刷分和数据漂移。
