## 外部公开 PDF 固定挑战集：首轮与修复后复测

源：jijunhao/SyntheticResumeData
固定 Git commit：3ecd09129f65955e743aacf67f2785fcee10d461
固定文件编号：1–10、101–105、201–205，共 20 个外部合成 PDF，分别使用相应的人工核对 GT JSON。
测量脚本：scripts/benchmark_external_resume_corpus.py
运行：uv run --python 3.12 python -m scripts.benchmark_external_resume_corpus

文件在内存中通过固定版本 Git 对象或 GitHub API 取得、解析、校验 SHA256；按需读取的外部 Git 对象缓存在操作系统临时目录（不属于 PaperPro 项目或版本库）。不会将原始简历或身份字段写入 PaperPro 仓库或测试日志；脚本不加入日常离线 CI。

本地多轮实测均为 2026-10-19，严格复用相同 Git commit、相同 20 份 PDF、相同 276 项字段定义和分母。除特别注明的失败旁路实验外，以下列出经过关键反例校验的稳定版本：

字段明细是每个 GT 已标注实体的命中率，不能推成所有真实简历完整率。该独立数据的 workExperience 也可能包含校园社团职责，和本产品的工作/实习定义不同，必须澄清映射而不是为了分数硬塞入工作经历。

真实原因之一已由原版 PDF 脱敏版式确认：例如中英双语“工作经历 / Experience”“教育背景 / Education”，以及“2022.07—至今：数据库工程师：某公司”等职位在前、公司在后的行。相关识别逻辑已做最小修改，见 app/parser.py、app/diagnosis/adapter.py 与 tests/test_synthetic_parsing_quality.py。

此前 50 个职位标签中有 23 个已位于经历标题却未被拆入 role 字段，尾部职位切分使职位命中升至 14/50。本轮又核实外部样本存在没有斜线分隔的中英双语标题，例如“实习经历Internship Experience”；增加严格限定的双语标题识别后，发现多栏联系信息可能落在经历区。仅加入标题识别的中间版本达到 166/276（60.14%），但**错误地把含手机号的日期行当成新增任职**，故不接受这一中间结果。经反例驱动改为联系字段全局唯一值兜底，并将含联系方式的经历行保留至未分类核对区（不参与任期计算），最终稳定结果 **163/276（59.06%）**，较原始版本增加 27 项、9.78 个百分点，较上轮稳定版增 7 项、2.54 个百分点。电话和邮箱补齐不是通过推断新事实，而是取自原文仅出现一次的实际值；多候选值时拒绝猜测。**仍未达到外部挑战集 90% 门槛**，后续需要独立分块与关系抽取验证，不能以继续堆叠正则掩盖这项结构瓶颈。

## 甲方演示步骤与验收口径

1. 首页上传 PDF/DOCX/DOC/PNG/JPG 或粘贴文本；验证格式限制、10MB 上限与加载反馈。
2. 在可编辑表单修正姓名、教育、工作公司、职位、起止年月、项目和证书；原文件 SHA256 不变。
3. 职位和公司两项都空则禁用生成按钮；填写至少一项后可继续。
4. 查看七类岗位要求的系数、有效权重、引用原文、总分、等级与 HR 视角边界说明。
5. 五维产出各自有证据和结论；关闭一维不影响其他维度。
6. 建议至少八项，每项有定位、问题或优化机会、建议和局部示例；高优先级只给可核对的过筛硬伤。
7. 勾选若干建议或面试核查条目，分别导出 TXT/PDF；未勾选的内容不会出现在文件中。
8. 报告提供时间、版本、规则版本；可选 DeepSeek 需要显式数据发送同意，模型无法改写规则算出的分数。
9. 移动端浏览器模拟完成选择与预览；其他两个智能体的 UI 与真实 iOS/Android 仍需独立验收。
10. 经典编辑器仍位于 /classic，settings.json 与私有 settings.local.json 正常。

## 结论分层（必须分别呈现）

- DEMO_PASS：R7–R10 的已实现产品功能，可现场操作和用 Chrome/Python 回归脚本验证。
- SYNTHETIC_PASS：20 份自行构造 DOCX/PDF 的 260/260 字段，四张高清模拟图片的 49/52 字段，1680 组反事实对照预期关系均成立。
- EXTERNAL_REFERENCE_BASELINE：固定 20 份外部合成 PDF 的结构化命中率依次为 49.28% → 51.81% → 56.52% → 59.06% → **60.51%（167/276）**；原文提取始终 92.39%。保留联系行不误建任职的防护；**仍未达到 90%**。
- NOT_VALIDATED：20 份真实自愿提供简历的统计准确率、真实手机拍摄与权限、美太内部评分细则、真实 HR 选拔结果、另外两个智能体风格统一。

推荐甲方描述：“PaperPro 的五步候选人诊断闭环已可演示；岗位评分可重复、可溯源，报告与清单可导出。外部多版式 PDF 结构解析及真实 HR 效度仍属后续专项验收。”

## 后续最小动作

已在同一 20 份 PDF 上先验证坐标整栏重排会退化（**152/276**，实验被否决），再实现只补充来源可追溯且原值缺失的姓名/教育的双视图机制（**167/276**，正式采用）；不改写公司、职位、任职日期、工作项目与 PDF 原文。相关源码：`app/diagnosis/pdf_layout.py`、`app/diagnosis/api.py`；失败实验可通过 `scripts/experiment_pdf_layout.py` 复现，正向/安全测试见 `tests/test_pdf_layout_complement.py`。

**独立 GT 的字段级接受审计：** `uv run --python 3.12 python -m scripts.audit_layout_complement`。固定 20 份外部合成 PDF 中，4 个此前空白的姓名被新机制补入，4 个均与独立 GT 相符（**该受控挑战集新增姓名的 4/4**，不是现实应用中的姓名识别准确率）；没有因辅助机制增加任何学历条目，未改变原文件 SHA、完整原文、现有工作经历、项目与技能。报告不输出个人身份原文，只给公开的合成样本编号和聚合数字。

## 带坐标的工作关系试验（保留人工确认，不自动写入）

先通过固定外部合成 PDF 的安全统计发现：有 9 个职位词仍出现在已解析经历标题但未进入 role 字段，其中 8 个可在 PDF 的独立文字 Span 找到，部分与日期、公司处于同一行。为了处理“日期—机构—职位”三段排版，在 `app/diagnosis/work_relation.py` 中实现了基于物理行和原文一致性的候选提案实验，并用虚构 PDF 编写失败反例与回归测试。

关键独立证据：第一次尝试自动写入时，同一固定外部 20 份 PDF 的结构化命中**仍为 167/276**；新填的唯一一项职位**不符合独立 GT 的职位/企业配对**，属于可复现的语义误判。因此取消自动写入，改成只返回 `review_hints`：每项具有 `source_path`、原始标题、候选机构/职位、`status=unverified`，没有任何字段或分数副作用。用户在第二步表单核对原件后可以自主“采纳”或“忽略”；更改对应经历字段会使旧提示失效。

复验命令：

    uv run --python 3.12 python -m scripts.profile_work_relation_gates
    uv run --python 3.12 python -m pytest tests/test_work_relation_geometry.py -q
    cd frontend && npm test -- --project=chromium e2e/candidate.spec.js -g "PDF work-role suggestions"

固定外部基准仍为 **167/276（60.51%）**；实验仅补齐“用户决定前不把几何假设写成个人履历事实”的工程闭环。对外不能宣传自动职位识别准确率增加。本轮不涉及收费 AI、真实 HR 标签或直接采集牛客个人简历。
