# PaperPro WorkBlock 二维版式区域候选实验（2026-10-19）

状态：代码、红绿测试、固定训练开发集对照已完成；**未达到替换现有解析器的条件，不部署。**

## 输入和边界

使用 Apache-2.0 SyntheticResumeData 的独立 GT 和固定 commit 3ecd09129f65955e743aacf67f2785fcee10d461。只访问编号 21–35 的 15 份训练开发 PDF；不读取验证 36–40、新冻结测试 41–60 和旧挑战集 1–10、101–105、201–205。

正式产品的外部 20 PDF→Schema 基准仍为 **167/276（60.51%）**。没有真实申请人数据、收费 AI、GPU 或模型训练，也没有更改正式简历解析、评分、文件内容、settings.json 或远程 GitHub。

## 实现

app/diagnosis/workblock_regions.py 使用 PyMuPDF 原生 PDF 文字行、页码、归一化坐标、保守分栏与已识别章节标题。检测到两个平行且具有独立标题的栏目时，按栏分别处理；否则不强迫整栏重排。WorkBlock 只能在明确的工作/实习区段中由合法短日期行发起；遇到下一条日期或另一类章节终止。项目、教育或职责正文中的日期不能创建工作经历。

每个候选保留区域文字、对应坐标、日期字符串与文件哈希；标记为 unverified。**不会**生成已确认公司、职位、真实雇佣关系、任职年限或用户评分；也没有接入生产 API。

## 与现有解析器的相同来源对照

训练开发池有 32 组第三方 GT 公司—职位配对：

| 指标 | 数量 |
|---|---:|
| 独立 GT 配对 | 32 |
| WorkBlock 候选区域 | 25 |
| 旧解析的经历 Entry | 27 |
| 公司与职位在同一个 WorkBlock 出现 | **17/32（53.13%）** |
| 公司、职位与起止年月在同一块且日期匹配 | **16/32（50%）** |
| 旧 Entry 的原文字段同段共现 | **19/32（59.38%）** |
| 旧 Entry 的公司和职位结构字段均正确 | **10/32（31.25%）** |
| 只被 WorkBlock 区域覆盖 | 4 |
| 只被旧 Entry 原文覆盖 | 6 |
| 两者都能覆盖 | 13 |
| 两者都漏掉 | 9 |
| 仅按原文字段共现计算的候选并集 | **23/32（71.88%）** |
| 没有对应 GT 配对的候选 WorkBlock | 9（**不能**直接称为假阳性） |

以上的区域共现不是语义关系验证，更不是自动字段抽取准确率。第三方的 workExperience 可能包括社团、校园实践；不能为了数字把这些内容自动写成正式工作经历。

## 研发决策

**不替换旧解析器。** WorkBlock 单独的同区域召回 17/32，低于旧解析原文 Entry 的 19/32。新旧各自可找回对方漏掉的配对，说明未来可以作为两路证据，但任何合并都必须有来源与冲突门禁，且未经人工确认不应写入任职。

上游真正瓶颈仍为多栏文字归属、非标准章节/日期和公司—职位关系。不是继续扩展日期正则。

## 复现

    uv run --python 3.12 python -m pytest tests/test_workblock_regions.py tests/test_workblock_benchmark.py -q
    uv run --python 3.12 python -m scripts.benchmark_workblock_regions

只显示计数和公开合成 PDF 编号，不输出原文、姓名、联系方式、公司名或职位。GT 一律在两种解析器生成候选之后读取；测试和代码均拒绝访问其他数据划分。

## 下一最小里程碑

优先让一套成熟文档版式引擎（如 Docling）与当前 PyMuPDF 在相同开发 PDF 上做只读章节/区域识别比较，再决定是否引入视觉版式模型。应同时评价章节归属、区域召回、完整字段组装、候选数量与误建雇佣风险。不要以候选并集或条件化排名替代正式 167/276 的验收口径。
